# 为什么你的删除功能突然失效了？—— 一个沉默已久的 JavaScript 精度陷阱

## 写在开头

前几天帮朋友排查一个问题：一个看似普通的删除功能，点击删除按钮后后端总是返回"记录不存在"。更诡异的是，列表明明显示着这条数据，点击删除却找不到。

排查到最后，竟然是和 JavaScript 处理大数字的方式有关。这是一个很多开发者都遇到过但容易忽略的问题。

## 先复现问题

### 后端数据库

```
表名: wo_work_order
id: 2042490503953403905 (雪花算法生成)
order_no: WO1775802658383
status: CREATED
```

### 前端调用删除

```javascript
const handleDelete = async (row) => {
  console.log('删除工单, id:', row.id)  // 输出: 2042490503953403905
  await deleteWorkOrder(row.id)
}
```

### 后端日志

```
删除工单, id=2042490503953403905
SELECT * FROM wo_work_order WHERE id=? AND deleted=0
==> Parameters: 2042490503953403905(Long)
<== Total: 0  // 没找到！
```

### 前端显示的错误

```
"工单不存在"
```

## 问题的真相

### 第一步：检查前端实际发送的值

```javascript
console.log('原始ID:', row.id)
console.log('转字符串:', String(row.id))
console.log('JSON序列化:', JSON.stringify({id: row.id}))
```

输出：
```
原始ID: 2042490503953403905
转字符串: 2042490503953403905
JSON序列化: {"id":2042490503953404000}  // 变了！
```

等等，JSON 序列化时 ID 居然变成了 `2042490503953404000`！

### 第二步：为什么会变？

JavaScript 使用 **IEEE 754 双精度浮点数**来表示所有数字。这是有精度限制的：

```javascript
Number.MAX_SAFE_INTEGER  // 9007199254740991
// 这是 JavaScript 能精确表示的最大整数
```

而我们的 ID 是 `2042490503953403905`，远超过这个数字。

```javascript
// 精度丢失演示
2042490503953403905 === 2042490503953404000
// true (在 JavaScript 眼里它们是同一个数字！)
```

### 第三步：二进制层面的解释

```
2042490503953403905 的二进制：
11101011100010101100101011001110001001000000000000001
              ↑ 这里开始精度丢失

JavaScript 只保留 53 位有效位，
超出的部分只能四舍五入。
```

## 解决方案

### 核心思路：不把大数字传给前端

让后端在返回 JSON 时，把 Long 类型的 ID 转成字符串。

### 后端实现（Spring Boot + Jackson）

```java
import com.fasterxml.jackson.databind.annotation.JsonSerialize;
import com.fasterxml.jackson.databind.ser.std.ToStringSerializer;

// 在实体类的 id 字段上添加注解
@JsonSerialize(using = ToStringSerializer.class)
private Long id;
```

现在 JSON 输出变为：

```json
{"id": "2042490503953403905", "orderNo": "WO1775802658383"}
```

注意：现在是字符串 `"2042490503953403905"`，不再丢失精度。

### 前端适配

之前只能接收数字：

```typescript
// 之前
export function deleteWorkOrder(id: number) {
  return request({ url: `/workorder/${id}`, method: 'delete' })
}
```

现在 string 和 number 都可以：

```typescript
// 之后
export function deleteWorkOrder(id: string | number) {
  return request({ url: `/workorder/${id}`, method: 'delete' })
}
```

URL 中的 `/workorder/${id}` 会自动把 id 转成字符串。

### 测试验证

修改后再来一遍：

```
后端日志：
删除工单, id=2042490503953403905
SELECT * FROM wo_work_order WHERE id=? AND deleted=0
==> Parameters: 2042490503953403905(Long)
<== Total: 1  // 找到了！

前端：删除成功！
```

## 进阶问题：乐观锁冲突

解决了精度问题后，我们又遇到了另一个错误：

```
org.apache.ibatis.binding.BindingException: 
Parameter 'MP_OPTLOCK_VERSION_ORIGINAL' not found.
```

这是因为实体类使用了 `@Version` 注解做乐观锁，手动 `updateById()` 时 MyBatis-Plus 会自动注入-version 条件。

**解决方案**：使用 `UpdateWrapper` 代替 `updateById()`

```java
// 错误的写法
order.setDeleted(1);
updateById(order);

// 正确的写法
var updateWrapper = new UpdateWrapper<WorkOrder>()
        .set("deleted", 1)
        .eq("id", id);
mapper.update(null, updateWrapper);
```

## 问题总结

| 问题 | 原因 | 解决方案 |
|-----|------|---------|
| 删除失败 | JavaScript 精度丢失 Long ID | 后端返回 String |
| 更新失败 | @Version 乐观锁冲突 | 使用 UpdateWrapper |

## 推荐配置

### 实体基类

```java
@Data
public abstract class BaseEntity {
    @TableId(type = IdType.ASSIGN_ID)
    @JsonSerialize(using = ToStringSerializer.class)
    private Long id;
    
    @TableLogic
    private Integer deleted;
    
    @Version
    private Integer version;
}
```

### API 返回

所有的 Long 类型 ID 都序列化为 String，前端无需关心精度问题。

## 写在最后

这个问题之所以容易被忽略，是因为：

1. 小规模项目 ID 通常较小，不会触发精度问题
2. 自增 ID 一般在 1-100000 范围内，完全安全
3. 只有使用雪花算法等分布式 ID 时才会暴露

但随着业务增长，一旦 ID 超过 9007199254740991，问题就会突然爆发。

建议：在项目初期就使用 ToStringSerializer 防患于未然。
